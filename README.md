# ВышКат — учёт парка кикшеринга

Консольное приложение на **C# / .NET 10** для учёта транспортных средств и инвентаря сервиса «ВышКат» — «Доедем до дедлайна».

В проекте используются принципы ООП и SOLID, DI-контейнер `Microsoft.Extensions.DependencyInjection` и модульные тесты на xUnit.

## Возможности

- Добавление электросамокатов, велосипедов и электровелосипедов.
- Добавление шлемов и зарядных станций.
- Приём транспортного средства только после решения сервисного центра (`IServiceCenter`).
- Отклонение неисправного транспорта.
- Проверка уникальности инвентарных номеров без учёта регистра.
- Проверка оценки простоты для новичка: целое число от 1 до 10 включительно.
- Формирование списка техники для новичков с оценкой от 6 до 10 включительно.
- Расчёт суммарного суточного энергопотребления объектов, реализующих `IEnergyConsumer`.
- Вывод количества транспортных средств, общего числа инвентарных объектов и полного списка с инвентарными номерами.
- Обработка некорректного ввода с объяснением ошибки и повторным запросом.
- Подтверждение действий ответами «да» или «нет».
- Демонстрация успешной и отклонённой приёмки через пункт меню 7.
- Завершение работы с сообщением «До свидания!».

## Требования

Для сборки и запуска требуется установленный **.NET 10 SDK**.

## Запуск

Все команды выполняются из корня репозитория.

Восстановление зависимостей:

```bash
dotnet restore
```

Сборка проекта:

```bash
dotnet build VyshKat.sln --configuration Release
```

Запуск приложения:

```bash
dotnet run --project src/VyshKat/VyshKat.csproj
```

Запуск тестов:

```bash
dotnet test VyshKat.sln --configuration Release
```

При первом запуске для восстановления пакетов NuGet необходимо подключение к соответствующим источникам пакетов.

### Назначение основных компонентов

## Архитектурные решения и SOLID

### SRP — Single Responsibility Principle

Каждый основной компонент отвечает за отдельную задачу:

- `Fleet` управляет составом парка и уникальностью инвентарных номеров.
- `ParkService` реализует бизнес-правило приёмки транспорта.
- `ReportService` формирует отчётные данные.
- `ConsoleApp` организует пользовательский сценарий и взаимодействие с консолью.

### OCP — Open/Closed Principle

Архитектура позволяет добавлять новые виды транспорта и инвентарные объекты без массового изменения бизнес-логики.

Новый потребитель энергии может реализовать `IEnergyConsumer`, чтобы его энергопотребление учитывалось при суммировании. Новый инвентарный объект может реализовать `IInventoryItem` или использовать базовый класс `InventoryItem`.

### LSP — Liskov Substitution Principle

Конкретные виды транспорта могут использоваться через общую абстракцию `Transport` и контракт `IRentableTransport`.
Потребители энергии обрабатываются через `IEnergyConsumer`, без необходимости знать конкретный тип устройства.

### ISP — Interface Segregation Principle

Контракты разделены по назначению:

- `IInventoryItem` описывает инвентаризацию.
- `IEnergyConsumer` описывает суточное энергопотребление.
- `IRentableTransport` описывает транспорт, доступный для аренды.

Например, обычный велосипед не обязан реализовывать `IEnergyConsumer`, поскольку не потребляет энергию в рамках принятой модели.

### DIP — Dependency Inversion Principle

`ParkService` зависит от абстракции `IServiceCenter`, а не от конкретной реализации сервисного центра. Благодаря этому в тестах можно подменять техосмотр fake-реализацией интерфейса.

Зависимости передаются через конструкторы, а их создание и регистрация сосредоточены в `Program.cs`.

## DI-контейнер

Для регистрации зависимостей используется `Microsoft.Extensions.DependencyInjection`.

В `Program.cs` настраивается контейнер зависимостей, включая `IServiceCenter`, `Fleet`, `ParkService`, `ReportService` и `ConsoleApp`.

Это позволяет отделить конфигурацию приложения от бизнес-логики и подменять реализации зависимостей при тестировании.

## Тестирование и покрытие

Для тестирования используется xUnit. Тесты проверяют:

- ограничения доменной модели;
- допустимость оценки простоты для новичка;
- запрет отрицательного энергопотребления;
- успешную и отклонённую приёмку транспорта;
- уникальность инвентарных номеров;
- суммирование суточного энергопотребления;
- формирование отчётов;
- разрешение зависимостей через DI-контейнер;
- поведение консольного приложения;
- повторный запуск демонстрационного сценария.

### Запуск тестов с измерением покрытия

Для измерения покрытия используется Coverlet через сборщик данных `XPlat Code Coverage`.

Из корня проекта выполни:

```bash
dotnet test VyshKat.sln --configuration Release --collect:"XPlat Code Coverage"
```

После выполнения команды отчёт `coverage.cobertura.xml` создаётся в отдельном каталоге внутри `tests/VyshKat.Tests/TestResults/`.

Чтобы найти отчёт в macOS или Linux:

```bash
find tests/VyshKat.Tests/TestResults -name coverage.cobertura.xml -print
```

Для просмотра покрытия строк кода подставить фактический путь к отчёту:

```bash
grep -o 'line-rate="[^"]*"' "<путь-к-отчёту>" | head -1
```

Атрибут `line-rate` содержит долю покрытых строк от 0 до 1. Для получения процента значение умножается на 100.

- **Ошибок:** 0.
- **Покрытие строк кода:** 81,63%.

Целевой ориентир задания — не менее 60% покрытия тестами. В последней проверенной версии этот порог выполнен.

## Ответы на обязательные вопросы

### 1. Какой принцип SOLID применён наиболее явно?

Наиболее явно применён DIP. `ParkService` использует интерфейс `IServiceCenter`, а не зависит от конкретного сервисного центра. В тестах реальную проверку можно заменить fake-реализацией, которая принимает или отклоняет транспорт по заданному сценарию.

### 2. Какой принцип сознательно ограничен или почти нарушен?

`ConsoleApp` отвечает за пользовательский ввод, вывод сообщений и организацию демонстрационных сценариев. Это объединяет несколько обязанностей на уровне консольного интерфейса.

Для небольшого учебного приложения такое упрощение допустимо. Если приложение будет расширяться, форматирование вывода и обработку пользовательского ввода можно выделить в отдельные компоненты.

### 3. Что изменится при расширении проекта?

**Новый вид транспорта.** Можно добавить новый класс-наследник `Transport` или `PoweredTransport` и реализовать необходимые контракты. Если транспорт потребляет энергию, он должен поддерживать `IEnergyConsumer`. Приёмка продолжит использовать абстракцию сервисного центра.

**Сотрудники.** Сотрудников следует представить отдельной доменной моделью и учитывать в отдельном сервисе, поскольку они не ставятся на баланс парка.

**Склад запасных частей.** Его можно реализовать как отдельный сервис с собственными правилами поступления, хранения и выдачи запчастей. Инвентаризируемые позиции при необходимости могут реализовывать `IInventoryItem`.

### 4. Как тестируется решение техосмотра и как подменяется зависимость?

Тесты успешной и неуспешной приёмки проверяют, добавляется ли транспорт в парк в зависимости от решения сервисного центра. Для изоляции бизнес-логики вместо реального `IServiceCenter` используется fake-реализация с заранее заданным результатом.

Отдельный тест проверяет правило для новичков: в соответствующий отчёт попадает транспорт с оценкой не ниже 6.

## Демонстрация работы

После запуска приложения доступно интерактивное меню:

1. Добавить электросамокат.
2. Добавить велосипед.
3. Добавить электровелосипед.
4. Добавить шлем.
5. Добавить зарядную станцию.
6. Показать отчёты.
7. Запустить демонстрационный сценарий.
0. Выход.

Программа поддерживает повторный ввод после исправимых ошибок. Пункт 7 демонстрирует успешную и отклонённую приёмку, а пункт 0 завершает работу приложения.
